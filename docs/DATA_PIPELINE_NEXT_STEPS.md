# 数据管线下一步执行文档

状态：诊断完成，等待按本文实施。

本文固定后续工作为两个 PR。不得在实施过程中继续拆分同一问题形成额外 PR；若出现与本文无关的问题，先记录并单独申请范围确认。

## 1. 生产诊断基线

诊断时间：2026-08-08（Asia/Shanghai）。生产版本：`9e0e9dcf3cbeecd62a922529ee4e633168fd04e5`。

- 主数据库约 1.1 GB；`runtime` 约 4.5 GB，其中备份目录约 3.4 GB。
- `feature_evidence` 约 164.6 万行，约 150 万行为 inactive 历史证据；过去 24 小时新增约 69.5 万行证据，其中约 59 万行很快失效。
- `game_documents` 和 `game_embeddings` 各约 36.6 万行，当前为全部约 18.2 万个 App 建立派生检索数据，而有效联机候选约 2.48 万个。
- `/admin/v1/data-status` 公网实测约 59 秒；页面在请求完成前只能显示空骨架。
- 当前联机候选 24,787；商店详情 99.7%、日期 99.8%、封面接近 100%，但评价仅 19.5%、CCU 仅 17.8%。
- 生产候选发现周期为 300 秒，明显短于代码默认的 6 小时；重复页处理持续制造证据历史和全库统计负载。
- 富化长期停留在 `store_first`，最近批次只处理商店详情，评价和 CCU 没有推进。
- 管理页任务 `coverage_ratio` 复用了同一个推荐档案覆盖率，不能表示各数据阶段的真实完成度；累计 dead job 也混入大量历史故障。

## 2. PR 1：停止数据库增长并恢复可观测性

建议分支：`codex/data-pipeline-observability`

### 2.1 范围

1. 证据写入幂等化。
   - `(app_id, feature_name, source_type)` 的有效值和来源未变化时，不新增历史行。
   - 只有事实内容变化时才停用旧证据并写入新证据。
   - 候选搜索页重复出现同一 App 时不得重复制造相同 `category_hint` 和派生画像证据。
2. 移除候选页热路径中的重复全库覆盖统计。
   - 页级日志使用本次写入数和轻量计数。
   - 完整 M3/M7 统计只由低频维护任务生成。
3. 拆分候选发现节奏。
   - 新游顶页轮询建议 15 分钟一次。
   - 深度 continuation 游标建议 6 小时一次。
   - 不再每 5 分钟重复处理 4 页约 400 行候选。
4. 建立轻量数据监测快照。
   - scheduler/worker 在任务完成时更新库存、各维度覆盖率、当前阶段、批次进度、最近错误和吞吐量。
   - `/admin/v1/data-status` 只读取快照和小表，不在 HTTP 请求内执行 M3/M7 全库审计。
   - dead job 分为“最近故障”和“历史累计”，默认页面不得用历史累计冒充当前失败。
5. 为证据历史增加明确保留策略和清理入口，但本 PR 不在生产执行大规模删除或 compact。

### 2.2 测试与验收

- 同一候选页连续入库两次，第二次不得增加相同有效证据行。
- 事实变化时保留一条旧历史和一条新有效证据。
- 候选采集测试证明顶页和 continuation 使用独立到期时间与游标。
- `/admin/v1/data-status` 在大型测试库中不调用 `m3_catalog_coverage`、`m7_data_coverage` 或四分区候选查询。
- 管理页分别显示商店详情、日期、评价、CCU、价格、语言和检索索引覆盖率。
- 本地 Rust/前端测试、Clippy、格式检查及 GitHub Actions 全绿。
- 部署后接口冷读目标小于 1 秒，连续读取目标小于 200 毫秒。
- 部署后观察至少 6 小时：重复证据增长应接近 0，候选发现任务不得持续占用大部分 worker 时间。

### 2.3 生产执行

- 只通过 GitHub Actions 构建 GHCR immutable 镜像。
- `ora_proxy` 只拉取并运行镜像，严禁在 VPS 编译。
- 先部署代码，再调整生产候选发现周期；不得只改周期掩盖重复写入问题。
- 本 PR 不删除现有历史数据，因此回滚只需恢复上一 immutable 镜像。

## 3. PR 2：新游一体化入库与受控存量清理

前置条件：PR 1 已部署并稳定观察至少 6 小时。

建议分支：`codex/integrated-game-ingestion`

### 3.1 范围

1. 新游在同一个可恢复 worker lease 中完成核心入库。
   - 候选发现后识别真正新增的 AppID。
   - 按 `appdetails -> review summary -> popular reviews -> CCU` 顺序获取核心数据。
   - 每个阶段短事务落库并记录进度；网络请求期间不得持有 SQLite 写事务。
   - 单次新增数量设上限，超出部分进入高优先级持久队列，不能因 30 分钟租约到期而丢失。
2. 取消全局 `store_first` 饥饿。
   - 新游优先一次获取全部核心维度。
   - 存量刷新按商店、评价、CCU、英文名称等独立配额推进。
   - Steam 已成功返回但字段为空时记录“已检查为空”，使用更长重试周期，不能每 24 小时无限重抓。
3. 缩小派生检索数据范围。
   - `game_documents`、`game_embeddings` 和 `game_fts` 默认只覆盖有效联机候选及明确人工关注对象。
   - 普通名称搜索继续使用 `app_name_fts`，不得因缩小向量索引而损坏 AppID/中英文名称搜索。
4. 提供可审计的存量清理命令。
   - 删除重复 inactive 证据，仅保留事实变化所需历史。
   - 删除非候选、非人工关注对象的派生检索文档、embedding 和 FTS 行。
   - 清理历史 completed/dead job 时保留近期诊断窗口和汇总计数。
   - 清理与 compact 分开执行，支持 dry-run、预计回收空间和中断前检查。
5. 备份保留数量单独参数化；建议从 3 份完整备份调整为 2 份，但必须在 compact 成功并验证恢复能力后执行。

### 3.2 测试与验收

- 新候选进入后，同一 worker 任务内可观察到商店详情、评价和 CCU 阶段依次完成。
- 中途模拟网络失败和进程退出，重启后从持久阶段恢复，不重复已完成请求，不丢 AppID。
- 商店空语言等终态不会在 24 小时后重新占满所有富化批次。
- 在固定调用预算下，评价和 CCU 覆盖率持续增长，任何维度不得长期为 0 吞吐。
- 非联机 App 清理后，名称搜索仍可命中；自然语言联机推荐结果不回归。
- 清理命令默认 dry-run；实际执行需要显式确认参数、最新备份和足够磁盘空间。
- GitHub Actions 全绿后才允许生产部署。

### 3.3 生产执行顺序

1. 部署 PR 2 镜像，但暂不运行删除和 compact。
2. 观察新游一体化入库至少 24 小时，确认评价和 CCU 吞吐恢复。
3. 使用 GHCR 镜像中的 dbtool 运行清理 dry-run，记录行数和预计回收空间。
4. 停止 server/worker，恢复租约，创建并验证部署前备份。
5. 执行有界删除并核对覆盖率、搜索结果和外键。
6. 仅在磁盘空间和维护窗口满足时执行 compact；完成后重新校验 schema、完整性和关键 API。
7. 启动 immutable 镜像，验证 `/health/ready`、数据监测、新游查询、日历、搜索和 worker 进度。
8. 稳定后再按保留策略清理旧备份。

## 4. 共同禁区

- 不在 `ora_proxy` 编译 Rust、Node 或 Docker 镜像。
- 不在 worker 运行时直接修改 SQLite 文件。
- 不把网络请求包在 SQLite 写事务中。
- 不为改善页面数字而伪造覆盖率、成功时间或终态数据。
- 不在没有 dry-run、可恢复备份和回滚步骤时运行批量删除、`VACUUM` 或文件替换。
- 不把上述两个 PR 再拆成连续的小修复 PR；超出范围的问题先记录，待这两个 PR 验收后另行评审。

## 5. 完成定义

两个 PR 均完成且生产验收通过后，必须同时满足：

- 数据监测页面可快速打开，并能准确判断 worker 当前阶段和真实覆盖进度。
- 新发现游戏在一个可恢复工作单元中完成核心数据入库，正常情况下无需等待后续轮转游标。
- 评价和 CCU 覆盖率持续增长，不再被商店字段重试饿死。
- 重复事实不再持续增加 inactive 证据。
- 派生检索数据范围与联机产品目标一致，数据库体积和每日增长率有可解释上限。
- 所有生产构建来自 GitHub Actions/GHCR，VPS 仅负责拉取和运行。
